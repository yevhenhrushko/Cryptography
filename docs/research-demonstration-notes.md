# Идеи дополнительных учебных демонстраций

Разбор предоставленного файла `Cryptography research.md` от 3 октября 2026 года.
Ниже — предложения для следующих лабораторных работ; перечисленные здесь дополнительные
демонстрации слабого RNG, padding oracle, ECDSA и XOR пока не реализованы.

## Что добавить к RSA

1. **Предсказуемая генерация ключей.** Создать учебный генератор с небольшим пространством
   начальных состояний, например 4096 вариантов. Перебрать состояния, повторить генерацию
   `p` и `q`, сравнить `n` с публичным ключом, затем восстановить приватную экспоненту
   и расшифровать `Hello World`. Это демонстрация недостатка энтропии, даже если сам
   модуль велик. Исторический пример — предсказуемый генератор Debian OpenSSL,
   [DSA-1571-1](https://lists.debian.org/debian-security-announce/2008/msg00152.html).
   Учебная модель не будет точным воспроизведением старой реализации OpenSSL.

2. **Bleichenbacher / padding oracle.** Локальный симулятор расшифрования RSA PKCS#1 v1.5
   сообщает только, правильно ли оформлено дополнение. Атакующий изменяет шифротекст
   и по ответам постепенно сужает диапазон возможных сообщений. Можно показывать
   число запросов, размер диапазона и восстановление `Hello World`.
   Нужен доступ к такому оракулу: одного публичного ключа и шифротекста недостаточно.
   Это восстановление сообщения, а не приватного ключа. Реальный пример —
   [ROBOT, описание авторов](https://robotattack.org/).

Начать удобнее с первого варианта: он использует существующие RSA-хелперы и позволяет
сравнить перебор состояний генератора с уже реализованным поиском общего множителя.
Винер, Хастад, малая публичная экспонента и общий простой множитель уже представлены
в проекте; повторять их как новые демонстрации не требуется.

## Отдельные темы за пределами RSA

- **Повтор nonce в ECDSA.** Подписать два разных сообщения одним ключом с одинаковым `k`.
  Для подписей `(r, s1)` и `(r, s2)` восстановить
  `k = (z1 - z2) * inverse(s1 - s2) mod q`, затем
  `d = (s1 * k - z1) * inverse(r) mod q`.
  Здесь `z1`, `z2` — предусмотренные ECDSA целочисленные представления хешей сообщений,
  `q` — порядок подгруппы; знаменатели должны быть обратимы.
  Формулы следуют из уравнения подписи; правила вычисления хеша и вариант получения
  `k` описаны в [RFC 6979](https://www.rfc-editor.org/rfc/rfc6979.html).
  Это отдельная лабораторная по подписям, а не расшифрование RSA.

- **Повтор потока XOR.** Для одного и того же потока `S` получить
  `C1 = M1 XOR S`, `C2 = M2 XOR S`, поэтому `C1 XOR C2 = M1 XOR M2`.
  Если известен соответствующий участок `M1`, этот участок `M2` восстанавливается
  непосредственно. Очень короткий наглядный пример ошибки повторного использования потока.

## Что исправить в исходном исследовании

- Утверждение о пригодности MD5 для паролей ошибочно. Нужна специализированная
  функция хеширования паролей с подходящими параметрами, например Argon2id;
  [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
  объясняет, почему быстрые MD5 и SHA-1 не подходят.
- X25519 относится к согласованию ключей ECDH; его нельзя перечислять как алгоритм
  цифровой подписи. См. [RFC 7748, раздел 6.1](https://www.rfc-editor.org/rfc/rfc7748#section-6.1).
- В учебной формуле ECDSA обозначения `m1` и `m2` необходимо заменить или явно определить
  как преобразованные хеши, а не сами строки сообщений; все операции выполняются по модулю `q`.

Документ полезен как список тем, но приведённые в нём даты, оценки сложности и рекомендации
не прошли полный аудит. Для реализации каждой лабораторной нужны проверенные первоисточники.
