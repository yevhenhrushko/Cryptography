## Blocking Issues (Changed Code)

**Medium — M1 подтверждён: формат не защищает структуру файла.**
`src/main/java/com/cryptography/rsa/RsaFileCipher.java:104-109,126-142,145-155`:
блоки независимо шифруются с одинаковой пустой меткой, затем независимо расшифровываются и склеиваются.
Обещание в строках 21–22 шире фактических гарантий.
Независимый воспроизводимый пример на синтетической паре в памяти подтвердил:

- перестановка первых двух блоков принимается; результат — 400 изменённых байт;
- усечение до одного блока принимается; результат — 190 байт;
- подстановка блока второго файла на ту же позицию принимается; результат — 400 смешанных байт.

Предложенная в ревью метка с `index` и `total` недостаточна для последнего сценария: у разных файлов
на одной позиции метки совпадут. Нужна защита всего контейнера и контекста конкретного файла.
Гибрид RSA-OAEP для отдельного случайного ключа файла и AEAD для данных — более подходящий путь.
Если требуется аутентификация отправителя, её следует задавать отдельно: любой владелец публичного ключа
может создать новый корректный шифротекст.

**Medium — M2 подтверждён по исходникам, с оговоркой о правах.**
`RsaHelper.java:412-425`: запись выполняется до ограничения прав; используются `CREATE` и
`TRUNCATE_EXISTING`; ошибка установки прав подавляется вместе с отсутствием POSIX-поддержки.
Риск перехода по существующему симлинку и окна доступа реален. Конкретные права `0644` зависят
от umask/ACL и не следуют из кода без проверки среды. Значения и права существующих ключей
я не проверял. Для нового файла нужны безопасное создание с правами сразу и обработка ошибок;
режим перезаписи, если он нужен, должен иметь отдельный явный контракт.

**Архитектура — согласен с замечанием о подмене `e`.**
`RsaHelper.java:135-143`: запрос `p=61, q=53, e=3` возвращает `e=7`.
Это независимо воспроизведено без файлов. Причина — отсутствие взаимной простоты с φ, а не составность `e`:
в этом примере исходная экспонента простая. Нужно либо отклонять такой запрос, либо документировать
подбор экспоненты как отдельное поведение. Делать это молча в API с заданной экспонентой нежелательно.

**Тесты — утверждение о трёх минутах обычного `test` неверно.**
`RsaPublicKeyAttackTest.java:27-28` содержит `@EnabledIfSystemProperty`.
Свойство `rsa.attack.enabled=true` выставляет только задача `rsaKeyAttackTest`.
В независимом запуске через обычный `test` этот класс дал `tests=1, skipped=1, failures=0`.
Сокращать его бюджет для обычного `test` не требуется. Полный набор тестов ядра здесь не запускался,
поэтому это не оценка общего времени всех остальных классов.

**Зависимости — утверждение «свежие, известных уязвимостей нет» неверно.**
`build.gradle:18-19` и фактический `runtimeClasspath` подтверждают `logback-classic/core:1.5.17`.
В [официальном выпуске 1.5.19](https://logback.qos.ch/news.html#1.5.19) указано исправление
CVE-2025-11226. В текущем runtimeClasspath нет Spring/Janino, конфигурация использует только
ConsoleAppender; практическая эксплуатация этой CVE в текущем приложении не установлена.
В обновлённом Security-разделе исходного отчёта CVE уже признана, а раздел Dependencies остался противоречащим ему.

**Security H1 и M3 — риск верен, приоритет и доказательства нужно уточнить.**
Textbook RSA здесь намеренно демонстрирует слабости, а CLI шифрует известную тестовую строку.
Само по себе это не High-дефект учебной демонстрации. Предупреждения в публичном API и разделение
учебного примитива с безопасной схемой полезны; обещать защиту реальных данных таким примитивом нельзя.
Ранние выходы OAEP в `RsaFileCipher.java:199-207` подтверждаются, но рабочего оракула и эксплуатации
Мангера отчёт не показывает. Один текст ошибки не гарантирует отсутствие побочного канала;
замена одного цикла на маски также не делает весь Java/BigInteger-путь константным по времени.
Заявленную другим агентом совместимость OAEP с JCA в этой проверке повторно не воспроизводил.

**Performance, Complexity и остальные архитектурные предложения.**
Общий `SecureRandom` действительно есть, но узкое место требует профиля или сравнения.
[Java 21](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/security/SecureRandom.html)
разрешает совместное использование и описывает зависимость синхронизации от провайдера.
Ускорение от `ThreadLocal` не доказано. Разделение `RsaHelper`, перенос утилиты случайного диапазона,
сокращение `Main.main` и JaCoCo — возможные улучшения сопровождения, не подтверждённые блокирующие дефекты.

**Documentation.** Быстрый старт генерации ключей и файлового сценария полезен.
Акцент README на атаках соответствует явному заданию пользователя. Отсутствие LICENSE подтверждено,
но выбор лицензии — решение владельца; публичность репозитория здесь не проверялась.
Лицензия собственного кода не меняет условия сторонних PDF. Например,
[HAC](https://cacr.uwaterloo.ca/hac/about/chap3.pdf) на первой странице отдельно ограничивает распространение копий.

**Отдельное исправление бюджета по последующему запросу пользователя.**
Прежний отказ `rsaAttackSeconds=300` воспроизведён unit-тестом. Теперь значение по умолчанию — 180,
допустимый диапазон — 1–3600; JUnit получает бюджет +20 с, Gradle — бюджет +30 с.
Тест с управляемыми монотонными часами проверяет продолжение после 180 с и остановку на границе 300 с.
Конфигурации Gradle независимо проверены: `300 -> 330 с`, `180 -> 210 с`.
Целевые проверки: 36 тестов прошли, 1 долгий тест пропущен обычной задачей `test`.
Пятиминутный эксперимент с пользовательским ключом не запускался.
